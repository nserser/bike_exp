Hierarchical M3 Profile Binning and Follow-up Experiments
==========================================================

Purpose
-------

This file specifies the next implementation step for the dependency-aware DFR
experiment pipeline.

The current same-key experiment produced an important result: the key-conditioned
tail is real, but the naive M3 scalar score is not yet useful. In the r=31, d=5,
t=1, T=4 run, the simple M2 diagnostic captured the bad-key tail, while the
packed/full M3 score diluted the useful signal and ranked keys poorly.

The next step is therefore:

    Replace naive M3 scoring with hierarchical profile binning that refines M2
    instead of overriding it, then rerun the same-key comparison and the t=2
    exact experiment.

This should be implemented before changing the paper theory. The goal is to test
whether the full structural profile can improve certification tightness or tail
prediction once it is used as a refinement of the strongest observed baseline,
rather than as an unnormalized scalar score.

Background from the Previous Run
--------------------------------

The latest same-key diagnostic run found:

    r = 31
    d = 5
    t = 1
    threshold schedule T = 4
    keys = 128

Observed key-conditioned failure distribution:

    123 keys had p_H = 0
    3 keys had p_H = 0.5
    2 keys had p_H = 1.0

Thus:

    bad-key mass = 5 / 128
    empirical average DFR = 0.02734375

This is useful because it shows a genuine static-key tail: most keys decode all
single-bit errors, while a small number of structurally bad keys dominate the
average failure rate.

The model comparison showed:

    M2 was useful:
        - all bad keys were captured by the highest-risk M2 bin;
        - M2 had the best tail L1 error and strongest bad-key recall.

    Naive M3 was not useful:
        - bad keys were spread across several M3 bins;
        - M3's packed scalar score appears to combine unrelated coordinates in a
          way that destroys the M2 signal.

Interpretation:

    The full profile idea is not disproved. The problem is likely the M3
    scoring/binning design. M3 should be a hierarchical refinement of M2, not a
    replacement that reorders keys by a packed aggregate score.

Definitions
-----------

Let each key H have the following available quantities:

    p_H:
        Exact measured key-conditioned failure probability.

    M0 score/bin:
        Baseline independence-only or coarse baseline diagnostic.

    M1 score/bin:
        Syndrome-weight-only diagnostic.

    M2 score/bin:
        Near-codeword/high-overlap diagnostic that performed well in the latest
        t=1 run.

    M3 old score/bin:
        Previous full-profile packed scalar score. This should be kept for
        comparison, but should no longer be the main full-profile model.

    Raw profile coordinates:
        The implementation should store these explicitly, not only as a packed
        integer:
            - D_max(H)
            - C4_loc(H)
            - overlap histogram Lambda_H(k), especially high-overlap counts
            - near-codeword overlap tail coordinates A_H^N(u)
            - gathering counts G_H(m, ell)
            - fixed-point / absorbing indicators B_H
            - max local weighted-overlap budget Omega_H
            - any per-key maximum clean counter statistic used for t=1

New Model: M3_hier
------------------

Implement a new model called:

    M3_hier

M3_hier must be a hierarchical bin, not a single unnormalized scalar score.

Core requirement:

    M3_hier must refine M2.

That means if two keys are in different M2 bins, M3_hier must keep that ordering
or separation. Additional structural coordinates may only split keys inside an
M2 bin; they must not override the primary M2 risk separation.

Suggested representation:

    M3_hier_bin(H) =
        (
            M2_bin(H),
            C4_bin(H),
            Dmax_bin(H),
            Gather_bin(H),
            Absorb_bin(H),
            Omega_bin(H)
        )

The exact coordinates can be adjusted based on what is available in the current
artifact, but M2_bin must be the first coordinate.

Do not compute M3_hier as:

    a * M2 + b * C4 + c * Dmax + ...

unless all coordinates are normalized and monotonicity is justified. For this
step, avoid weighted scalar scores. Use tuple bins.

Primary monotonic ordering for risk ranking:

    Sort M3_hier keys lexicographically by:
        1. M2_bin descending, if larger M2 means higher risk;
        2. then by refinement coordinates descending only if larger means higher risk.

If any coordinate has the opposite direction, normalize it before sorting or
store an explicit "risk_direction" metadata field.

Important:

    The first version of M3_hier should be conservative and simple. Its purpose
    is to preserve M2's bad-key recall while testing whether additional profile
    coordinates improve tightness inside high-M2 bins.

Task 3: Add Bad-Key Recall Metrics
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The previous metrics used tail L1 error, top-10% recall, and Spearman
correlation. Keep them, but add metrics that are more appropriate for sparse
bad-key tails.

Define bad keys as:

    bad_any:
        p_H > 0

    bad_high:
        p_H >= 0.5

    bad_catastrophic:
        p_H = 1

For each model M0, M1, M2, M3_old, M3_hier compute:

    bad_any_recall_at_highest_bin
    bad_high_recall_at_highest_bin
    bad_catastrophic_recall_at_highest_bin

    bad_any_precision_at_highest_bin
    bad_high_precision_at_highest_bin
    bad_catastrophic_precision_at_highest_bin

    bad_any_recall_at_top_k
    bad_high_recall_at_top_k
    bad_catastrophic_recall_at_top_k

Use:

    k = ceil(0.10 * number_of_keys)

Also compute:

    tail_l1_error
    Spearman correlation with p_H
    Kendall correlation with p_H
    AUC if p_H > 0 is used as a binary label
    maximum p_H per bin
    mean p_H per bin
    key count per bin

Important metric convention:

    Larger model score/rank must mean higher predicted risk.

Before reporting Spearman/Kendall, verify that the sign is correct. The previous
run appeared to have a possible metric-sign issue.

Task 4: Direct-Bin and Certified-Bin Bounds
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

For each model bin, compute:

    p_bin_mean = average p_H in bin
    p_bin_max  = maximum p_H in bin
    bin_mass   = number of keys in bin / total keys

For certification-style plots and tables, use p_bin_max as the direct empirical
upper bound for keys in the bin.

For each model, compute:

    direct average bound:
        sum_over_bins bin_mass * p_bin_max

    empirical average:
        average p_H over all keys

    looseness:
        direct_bound / empirical_average
        if empirical_average = 0, report NA

    tail bound at thresholds tau:
        sum of bin_mass for bins with p_bin_max > tau

Use tau grid:

    tau in {0, 0.01, 0.05, 0.1, 0.25, 0.5, 0.75, 0.99}

Task 5: Static-Key Multi-Query Illustration
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

For each model's direct-bin certificate, compute:

    Fail_q_bound =
        sum_over_bins bin_mass * (1 - (1 - p_bin_max)^q)

Compare with empirical:

    Fail_q_empirical =
        average_over_keys (1 - (1 - p_H)^q)

Compare with average-only union bound:

    q * empirical_average, capped at 1

Use:

    q in {1, 2, 5, 10, 25, 50, 100}

Required output:

    static_key_bounds.csv

Columns:

    run_id
    model
    q
    empirical_fail_q
    profile_bound_fail_q
    average_union_bound
    profile_bound_looseness

Experiment Acceptance Criteria
------------------------------

A result is paper-useful if at least one of the following holds.

Strong success:

    M3_hier preserves M2's bad-key recall and improves at least one of:
        - tail L1 error;
        - profile-bound looseness;
        - static-key bound tightness;
        - separation inside the highest M2 bin.

Moderate success:

    M3_hier matches M2 and provides better interpretability through structural
    sub-bins, even if it does not improve numerical error.

Negative but useful:

    M3_hier does not beat M2. In this case, the paper should state that, in the
    first exact toy regime, the near-codeword/high-overlap coordinate is the
    dominant profile feature and the remaining coordinates do not improve the
    predictor. This is still publishable as honest evidence for the framework, but
    not as evidence that the full profile is always better.

Failure / stop condition:

    If t=2 is saturated again, rerun threshold sweep around:
        5;4;3;3
        4;3;3;3
        4;4;4;3
        5;5;4;3
        3;3;3;3

    If t=1 or t=2 results contradict the sanity checks, rerun:
        zero_error_sanity
        single_bit_geometry
        syndrome_update_consistency

Recommended Paper Interpretation
--------------------------------

If M3_hier succeeds:

    "The full structural profile is useful when used as a hierarchical
    certificate refinement: the strongest near-codeword/high-overlap coordinate
    identifies the bad-key tail, while additional dependency coordinates refine
    the upper bound inside that tail."

If M3_hier only matches M2:

    "The toy experiment shows that the key-conditioned framework exposes a
    structural tail, and that the dominant coordinate in this regime is the
    near-codeword/high-overlap feature. This motivates using the full profile as
    a certificate interface rather than forcing a single scalar score."

If M3_hier fails:

    "The full-profile scalar/binned model is too coarse for the current regime.
    The paper should keep the theorem framework, but the empirical section should
    emphasize the simpler M2 tail diagnostic and list profile refinement as an
    open implementation item."
