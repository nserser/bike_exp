DFR EXPERIMENT DIAGNOSTIC PLAN FOR CODEX
=========================================

Purpose
-------
Before changing the paper theory, diagnose why the current reduced-parameter runs have p_H close to 1. The goal is to determine whether the issue is:

1. a decoder implementation/convention bug;
2. a bad threshold schedule for the toy parameters;
3. a toy-parameter regime that is intrinsically too hard or degenerate;
4. or, only after those are ruled out, an uninformative structural-profile model.

Do not edit the paper theory in this task. Work only on the experiment/implementation side and produce diagnostic artifacts that can later be summarized in the paper.

Expected Repository Context
---------------------------
The repository should contain the Step 09 paper/source artifact and the experiment code used to generate:

- run_summary.csv
- combined_metrics.csv
- rare_event_summary.csv
- summary.md

If the repository layout differs, first locate the modules that implement:

- QC-MDPC key generation and syndrome computation;
- circulant/rotation conventions;
- threshold bit-flipping decoding;
- model summaries M0/M1/M2/M3;
- experiment configs and result aggregation.

Do not assume the current decoder is correct. Add direct invariant tests.

High-Level Deliverables
-----------------------
Create a new diagnostic run layer with:

1. unit/invariant tests for syndrome geometry and decoder update consistency;
2. zero-error and single-error sanity experiments;
3. true-bit versus clean-bit counter-distribution diagnostics;
4. threshold-sweep experiments to find a non-saturated regime;
5. failure-taxonomy output separating timeout, wrong-zero, nonzero halt, and divergence-like behavior;
6. unified same-key M0/M1/M2/M3 comparisons only after a non-saturated decoder regime is found;
7. a machine-readable summary file explaining whether the current p_H close to 1 is caused by implementation, thresholds, parameters, or model weakness.

Diagnostic Step 1: Zero-Error Sanity
------------------------------------
Goal:
Verify that the decoder succeeds on the zero error.

Procedure:
For each sampled key H at r=13,d=3 and r=31,d=5:

1. set e = 0;
2. compute s = e H^T;
3. run the decoder;
4. check that the output error estimate equals e;
5. check that the final residual syndrome is zero.

Expected result:
Every run succeeds. p_H at t=0 must be exactly 0.

Hard failure condition:
If any zero-error case fails, stop later diagnostics and fix the decoder initialization, success check, syndrome computation, or output comparison.

Diagnostic Step 2: Single-Bit Geometry Test
-------------------------------------------
Goal:
Check rotation and column-neighborhood conventions.

For each key H and each bit j:

1. set e = unit vector at j;
2. compute s = e H^T;
3. compute counter sigma_j = |Gamma_H(j) cap Supp(s)|;
4. check sigma_j == d;
5. check syndrome weight is d unless duplicate/collision conventions imply otherwise; record the actual syndrome weight.

Expected result:
The correct bit j should have observed_true_counter == d for every single-bit error.

Hard failure condition:
If observed_true_counter != d for any nondegenerate key/bit, the syndrome or Gamma_H convention is inconsistent. Inspect:

- whether circulant shifts use +z or -z consistently;
- whether syndrome computation and counter computation use the same block order;
- whether matrix transposition is implemented consistently;
- whether support indexing is modulo r in all places.

Do not proceed to model comparison until this passes.

Diagnostic Step 3: Incremental Syndrome Update Consistency
----------------------------------------------------------
Goal:
Verify that the decoder's incremental update matches recomputation from residual errors.

During every decoding run:

1. maintain the decoder's incremental syndrome s_i;
2. also recompute s_i_recomputed = syndrome(e + e_hat_i, H) from scratch;
3. assert or record whether s_i == s_i_recomputed;
4. record both syndrome weights and the flip count.

Expected result:
s_i and s_i_recomputed must match at every iteration.

Hard failure condition:
If any mismatch occurs, fix the syndrome update rule:

s_{i+1} = s_i + sum_{j in F_i} H_j

with addition over F_2, using the same column H_j convention as the syndrome function.

Diagnostic Step 4: Counter Separation
-------------------------------------
Goal:
Determine whether a useful threshold exists for the current toy regime.

For selected parameters:

- r=13,d=3,t in {1,2,3};
- r=31,d=5,t in {1,2,3,4};

sample or enumerate errors and collect first-iteration counters for:

- true residual bits j in E;
- clean bits j not in E.

Produce counter_distributions.csv.

For each parameter triple, compute:

- min/median/max true-bit counter;
- min/median/max clean-bit counter;
- overlap between the true and clean counter histograms;
- candidate thresholds T that maximize true-positive/false-positive separation.

Interpretation:

1. If true counters are usually high and clean counters low, the decoder geometry is likely correct and the threshold schedule should be tuned.
2. If true and clean counters are indistinguishable even at t=1, suspect an implementation/convention bug.
3. If separation exists at t=1 but disappears at t=3 or t=4, the toy parameter is simply too hard at those t values.

Diagnostic Step 5: Threshold Sweep
----------------------------------
Goal:
Find a non-saturated decoder regime where p_H is neither near 0 nor near 1.

Run threshold sweeps before comparing M0/M1/M2/M3.

Recommended sweep:

For r=13,d=3:
- t in {1,2,3}
- max_iterations in {1,2,3,5,10}
- constant thresholds T in {1,2,3}
- optional schedules: [3,2,2,1], [2,2,1,1], [2,1,1]

For r=31,d=5:
- t in {1,2,3,4}
- max_iterations in {1,2,3,5,10}
- constant thresholds T in {2,3,4,5}
- optional schedules: [5,4,4,3], [4,4,3,3], [4,3,3,2], [3,3,2,2]

For each setting, compute p_h_mean, p_h_min, p_h_median, p_h_max, and failure taxonomy.

Target regime:
Find at least one setting with:

- t=1 has near-perfect success;
- at least one larger t has p_h_mean in a non-saturated range, ideally 0.001 <= p_h_mean <= 0.5 for toy exploration;
- p_H varies across keys enough to support ranking/correlation experiments.

Do not proceed to M0/M1/M2/M3 comparison if all candidate settings have p_h_mean > 0.95 or p_h_mean < 1e-6.

Diagnostic Step 6: Failure Taxonomy
-----------------------------------
Goal:
Explain why failures occur.

For every threshold-sweep run, classify each decoding outcome as:

- success: recovered error equals sampled error;
- timeout: iteration bound reached with nonzero residual;
- wrong_zero: syndrome becomes zero but recovered error does not equal sampled error;
- nonzero_halt: decoder halts with nonzero syndrome, if such a halt rule exists;
- divergence_like: residual weight or flip count grows beyond a configured warning threshold.

Important:
Wrong-zero must remain a failure under the paper's correctness model. Do not change the success criterion to zero syndrome only.

Interpretation:

1. Many wrong_zero failures at tiny parameters may indicate degenerate toy codes with low-weight codewords/collisions.
2. Many timeout failures may indicate thresholds are too high or the decoder is not making progress.
3. Many divergence_like failures may indicate thresholds are too low or false flips dominate.
4. A mix of failure types is acceptable, but report it clearly.

Diagnostic Step 7: Unified Same-Key M0/M1/M2/M3 Comparison
----------------------------------------------------------
Goal:
Only after a non-saturated regime is found, compare model diagnostics fairly.

Important rule:
All four models M0, M1, M2, M3 must be evaluated on exactly the same keys and errors. The previous split runs had different configured_key_count values, so they were not suitable for strong model comparison.

Procedure:

1. Select a parameter/threshold setting from Step 5 with non-saturated p_H.
2. Generate one key list and save it as artifacts/diagnostics/shared_keys.jsonl or equivalent.
3. Generate or enumerate one error set per key and save the random seed/config.
4. Compute exact or sampled p_H for each key.
5. Compute M0, M1, M2, M3 scores/bins for every same key.
6. Save unified_model_comparison.csv.
7. Compute ranking summary metrics:
   - Spearman correlation with p_H;
   - Pearson correlation with p_H, if meaningful;
   - tail L1 error over a fixed tau grid;
   - top-10-percent recall for identifying high-p_H keys;
   - coverage/looseness only for models that claim an upper bound.

Acceptance condition for paper usefulness:
M3 should improve at least one meaningful tail/ranking metric over M0/M1/M2 in the non-saturated regime, or the paper must explicitly report that the full profile did not outperform simpler features in this pilot setting.

Diagnostic Step 8: Rare-Event Conditioning Only After Non-Saturation
--------------------------------------------------------------------
Goal:
Use near-codeword-overlap conditioning to test error-floor mechanisms, but only after the unconditioned run is not saturated.

Do not interpret rare-event conditional failure rates if unconditioned p_H is already near 1.

Procedure:
For the selected non-saturated setting:

1. compute U_H(E) for each error;
2. condition on U_H(E) >= u for u values with nontrivial but not overwhelming tail mass;
3. report:
   - tail mass A_H(u);
   - conditional failure probability Pr[failure | U_H(E) >= u];
   - contribution proxy A_H(u) * Pr[failure | U_H(E) >= u].

Interpretation:
A useful near-codeword result should show conditional failure substantially higher than unconditional p_H, while the tail mass is small enough to represent a meaningful stress region.

Implementation Details and Guardrails
-------------------------------------
1. Determinism:
   Every diagnostic run must record:
   - git commit or source hash if available;
   - random seed;
   - parameter triple;
   - threshold schedule;
   - max iterations;
   - key count;
   - error handling mode: exact, sampled, or sampled without replacement.

2. Docker-only execution:
   Provide commands through Docker. Do not require host Python packages.

3. No paper-theory edits:
   Do not modify LaTeX theory sections in this diagnostic task. It is acceptable to generate a diagnostics_summary.md that can later be imported into the paper.

4. Avoid false positives:
   If a diagnostic test fails, mark downstream results as invalid rather than continuing silently.

5. Same-key comparison:
   M0/M1/M2/M3 comparisons must use the same keys, the same errors, and the same decoder outputs.

At the end, generate artifacts/diagnostics/diagnostics_summary.md with these sections:

1. Executive verdict
   One of:
   - implementation/convention bug found;
   - threshold schedule problem found;
   - toy parameter regime too hard/degenerate;
   - non-saturated regime found and ready for model comparison;
   - structural-profile model not yet supported.

2. Sanity test results
   Include zero-error pass rate, single-bit geometry pass rate, and syndrome update consistency pass rate.

3. Threshold sweep conclusion
   List the best non-saturated settings, if any.

4. Failure taxonomy
   Explain whether failures are mostly timeout, wrong-zero, nonzero halt, or divergence-like.

5. M0/M1/M2/M3 comparison
   Include only if same-key unified comparison was run.

6. Recommendation for the paper
   State whether current results are:
   - only pipeline sanity checks;
   - usable as a small diagnostic experiment;
   - usable as evidence for M3 profile-tail improvement;
   - or not yet usable.

Stop/Go Criteria
----------------
Stop and fix implementation if:

1. t=0 does not always succeed;
2. single-bit true counter is not d;
3. incremental syndrome differs from recomputed syndrome;
4. M0/M1/M2/M3 are compared on different key sets;
5. failure taxonomy cannot separate wrong-zero from timeout/nonzero failures.

Proceed to paper-facing experiments if:

1. all invariant tests pass;
2. a non-saturated threshold/parameter regime is found;
3. p_H varies across keys;
4. M0/M1/M2/M3 are evaluated on the same keys/errors;
5. rare-event conditioning is run only after the unconditioned regime is meaningful.

Likely Interpretations
----------------------
If zero-error or single-bit geometry fails:
The issue is an implementation/convention bug, not a paper-theory issue.

If geometry passes but t=1 fails heavily:
The threshold schedule or decoder update policy is likely wrong for the toy parameters.

If t=1 succeeds but t=3 or t=4 saturates near p_H=1:
The toy setting is too hard. Use lower t or larger r, or tune thresholds.

If a non-saturated regime is found but M3 does not improve over M1/M2:
The structural profile may be too coarse or redundant. Report honestly and consider profile refinement later.

If M3 improves tail ranking or top-tail recall:
The results are interesting for the paper and should be converted into a compact experimental section.
